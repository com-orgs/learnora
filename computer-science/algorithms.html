Algorithms and Flowcharts

An algorithm is a precise sequence of steps for solving a problem. It can be written in everyday language, pseudocode or code. A flowchart makes the logic visible so that another person can follow and test it.

Learning time: 40–45 minutes · Beginner level · Free study resource

What you will learn

  • Define an algorithm and explain why clear, ordered steps matter.
  • Break a task into small steps that another person — or a computer — can follow.
  • Use the three control structures: sequence, selection and repetition.
  • Read and draw flowcharts using the standard symbols.
  • Trace linear search and binary search step by step, and count the comparisons.
  • Trace selection sort and bubble sort, and compare how much work each one does.
  • Test an algorithm with normal, boundary and empty cases.

1. What is an algorithm?

An algorithm is a precise sequence of steps for solving a problem. It has a clear starting point, each step does one clear thing, the steps are in an order that matters, and there is a clear finishing point. A recipe is an algorithm. So is the set of instructions for borrowing a library book, or for finding the largest number in a list.

Good algorithms have three qualities. They are unambiguous: every step means exactly one thing, so two people following them get the same result. They are finite: they finish — they do not go on forever. And they are correct: they solve the problem they claim to solve, for every allowed input, not just the easy ones.

Algorithms can be written in everyday language, in pseudocode (a half-formal way of writing steps that looks a little like code but is meant for people), or in a real programming language. Pseudocode is useful because it is precise enough to test by hand, but simple enough to read without knowing a language. In this lesson, pseudocode uses capital words for actions — READ, SET, IF, DISPLAY — and ordinary words for the rest.

Worked example 1 — an everyday algorithm. Making a cup of tea: 1. Fill the kettle with water. 2. Switch the kettle on. 3. Wait until the water boils. 4. Put a tea bag in a cup. 5. Pour the boiling water into the cup. 6. Wait 3 minutes. 7. Remove the tea bag. Step 3 matters: if you pour before the water boils, the tea is weak. Step 6 matters: skipping the wait gives weak tea too. Check: follow the steps in order and the result is tea; swap steps 3 and 5 and it is not.
Worked example 2 — largest of two numbers. Goal: display the larger of two numbers, A and B. Pseudocode: 1. READ A and B. 2. IF A is greater than B, DISPLAY A. 3. OTHERWISE, DISPLAY B. Trace it with A = 7 and B = 12: step 2 asks "Is 7 greater than 12?" — no. Step 3 displays 12. Correct. Trace it with A = 9 and B = 9: step 2 asks "Is 9 greater than 9?" — no. Step 3 displays 9. Correct — when the numbers are equal, either one is the largest. Check: the algorithm works for equal values too, because the OTHERWISE branch covers them.

2. Sequence: steps in order

Sequence means instructions run in order, one after another. It is the simplest control structure, and it is also the easiest to get wrong — because changing the order can change the result completely. "Put on your shoes, then tie your laces" works. "Tie your laces, then put on your shoes" does not.

When you design an algorithm, start by writing the steps in order, then check the order by tracing: follow the steps yourself with a real example and see whether the result is right. If a step needs the result of an earlier step, the order is forced. If two steps do not depend on each other, their order may not matter — but say so, rather than assuming it.

Worked example 3 — order matters. Algorithm for the average of three test scores: 1. READ score1, score2, score3. 2. SET total TO score1 + score2 + score3. 3. SET average TO total / 3. 4. DISPLAY average. Trace with scores 8, 9 and 7: total = 24, average = 24 / 3 = 8. Correct. Now swap steps 2 and 3: average = total / 3 before total is set — total has no value yet, so the algorithm fails. Check: a step that uses a value must come after the step that creates that value.

3. Selection: choosing a path

Selection (a decision) chooses between two or more paths depending on a condition. The usual form is IF … THEN … ELSE …: if the condition is true, follow one path; if it is false, follow the other. Selection is how an algorithm handles different cases instead of treating everything the same.

Conditions are yes-or-no questions about the data: "Is the score at least 50?", "Is the number even?", "Is the password correct?" A condition must be testable — it must have a definite true or false answer for every input. "Is the number big?" is not a good condition, because "big" is not defined. "Is the number greater than 100?" is a good condition.

Worked example 4 — pass or fail. A school passes a pupil who scores 50 or more out of 100. Pseudocode: 1. READ score. 2. IF score is at least 50, DISPLAY "Pass". 3. ELSE, DISPLAY "Fail". Trace with score = 50: the condition "50 is at least 50" is true, so display "Pass". Trace with score = 49: the condition is false, so display "Fail". Check the boundary: 50 is the first passing score, so test 49 and 50 — the values on either side of the boundary — not just 80 and 20.
Worked example 5 — even or odd. To test whether a number is even, check its remainder when divided by 2. Pseudocode: 1. READ number. 2. IF number MOD 2 equals 0, DISPLAY "Even". 3. ELSE, DISPLAY "Odd". Trace with number = 14: 14 MOD 2 = 0, so display "Even". Trace with number = 27: 27 MOD 2 = 1, so display "Odd". Trace with number = 0: 0 MOD 2 = 0, so display "Even" — zero is even, and a good algorithm gets boundary cases right. Check: three traces, including the boundary value 0, all correct.

4. Repetition: doing it again

Repetition (a loop, also called iteration) runs a block of instructions more than once. There are two common forms. A counted loop runs a fixed number of times: "FOR each item in the list, do this." A condition loop runs until something changes: "WHILE the total is less than 100, keep adding." Repetition is what makes computers powerful — a computer can repeat a simple step a million times without getting bored or making a copying mistake.

Every loop needs a way to stop. A counted loop stops when the count is reached. A condition loop stops when its condition becomes false. A loop with no way to stop is an infinite loop — the program never finishes. When you design a loop, always say what makes it stop, and trace it to prove that it does.

Worked example 6 — adding a list with a loop. Add the numbers 4, 7 and 9. Pseudocode: 1. SET total TO 0. 2. FOR each number in the list [4, 7, 9]: ADD the number TO total. 3. DISPLAY total. Trace it in a table: start total = 0; after 4, total = 4; after 7, total = 11; after 9, total = 20. Display 20. Check: 4 + 7 + 9 = 20. The trace table is the proof — it shows the value of total after every step.
Worked example 7 — sum of 1 to 5. Pseudocode: 1. SET total TO 0. 2. SET n TO 1. 3. WHILE n is less than or equal to 5: ADD n TO total; ADD 1 TO n. 4. DISPLAY total. Trace: total = 0, n = 1 → total = 1, n = 2 → total = 3, n = 3 → total = 6, n = 4 → total = 10, n = 5 → total = 15, n = 6. Now n = 6, which is not less than or equal to 5, so the loop stops and the program displays 15. Check: 1 + 2 + 3 + 4 + 5 = 15. Notice the loop ran 5 times, and the stopping condition (n = 6) is what ended it.

5. Flowcharts: seeing the logic

A flowchart draws an algorithm as boxes joined by arrows. Each shape has one meaning: an oval marks Start or End; a rectangle is a process (a calculation or an action); a parallelogram is input or output; a diamond is a decision, with two arrows leaving it labelled Yes and No. Arrows show the direction of flow.

Flowcharts are useful because they make the structure visible: you can see at a glance where a decision branches, where a loop goes back, and whether every path reaches End. A common flowchart mistake is a decision diamond with unlabelled branches — if you cannot tell which arrow is Yes and which is No, the flowchart is ambiguous. Another is a loop with no arrow back to the decision, which means the loop can never repeat.

Worked example 8 — flowchart for a library fine. A library charges a fine of 10 pence per day late, but no fine if the book is on time. Flowchart: Start (oval) → "Enter days late" (parallelogram, input) → diamond: "days late greater than 0?" → Yes branch: rectangle "fine = days late × 10" → parallelogram "Display fine" → End. No branch: parallelogram "Display no fine" → End. Trace with 3 days late: the diamond asks "3 greater than 0?" — Yes — fine = 3 × 10 = 30 pence. Display 30. Trace with 0 days: the diamond asks "0 greater than 0?" — No — display "no fine". Check: both branches reach End, and the Yes/No labels make the decision clear.

6. Searching: linear search and binary search

Searching is one of the most common jobs in computing: is this value in the list, and where? Linear search checks each item in order, from the first to the last, until it finds the value or runs out of items. It works on any list, sorted or not. Its cost is easy to count: in the worst case it checks every item.

Binary search is faster, but it only works on a sorted list. It looks at the middle item: if that is the value, it is done; if the value is smaller, it searches the left half; if larger, the right half. Each step throws away half the list, so it needs far fewer checks than linear search on a long list. The catch is the sorting: if the list is not sorted, binary search gives wrong answers.

Worked example 9 — linear search. Find 12 in the list [4, 7, 9, 12, 15]. Step 1: compare 4 — no. Step 2: compare 7 — no. Step 3: compare 9 — no. Step 4: compare 12 — yes, found at position 4. That took 4 comparisons. If the list had been searched for 15, it would have taken 5 comparisons — the worst case for a list of 5 items. Check: linear search on a list of N items needs at most N comparisons.
Worked example 10 — binary search. Find 15 in the sorted list [4, 7, 9, 12, 15]. Step 1: the middle item is 9. 15 is greater than 9, so ignore the left half. Step 2: the remaining list is [12, 15]; its middle item is 12. 15 is greater than 12, so ignore the left half. Step 3: the remaining list is [15]; the middle item is 15 — found. That took 3 comparisons, where linear search would also have taken 5 here. Check: each step halved the list (5 → 2 → 1). Now find 4 in the same list: middle is 9, 4 is smaller, so search [4, 7]; middle is 4 — found in 2 comparisons. Check: binary search needs the list sorted, and it throws away half the list at each step.

7. Sorting: selection sort and bubble sort

Sorting puts a list in order. Selection sort works by repeatedly finding the smallest remaining item and moving it to the front. On each pass, it scans the unsorted part, finds the smallest value, and swaps it into place. It is easy to understand, but it does a lot of comparing: for a list of N items, it makes roughly N × N comparisons.

Bubble sort works by comparing neighbours and swapping them if they are in the wrong order. After one full pass, the largest item has "bubbled" to the end. Repeat until a pass makes no swaps — that is the signal that the list is sorted. Bubble sort is also simple, and it can stop early on a list that is already sorted.

Worked example 11 — selection sort. Sort [5, 2, 4, 1, 3]. Pass 1: the smallest of all five is 1, so swap it with the first item: [1, 2, 4, 5, 3]. Pass 2: the smallest of [2, 4, 5, 3] is 2, already in place: [1, 2, 4, 5, 3]. Pass 3: the smallest of [4, 5, 3] is 3, swap it with 4: [1, 2, 3, 5, 4]. Pass 4: the smallest of [5, 4] is 4, swap: [1, 2, 3, 4, 5]. Sorted. Check: the list is in order, and each pass fixed one more position from the left.
Worked example 12 — bubble sort, one pass. Sort [5, 2, 4, 1, 3], first pass only. Compare 5 and 2 — swap: [2, 5, 4, 1, 3]. Compare 5 and 4 — swap: [2, 4, 5, 1, 3]. Compare 5 and 1 — swap: [2, 4, 1, 5, 3]. Compare 5 and 3 — swap: [2, 4, 1, 3, 5]. One pass made 4 swaps and moved the largest value, 5, to the end — as it should. Check: after pass 1, the last item is always the largest. The list is not sorted yet; more passes are needed.

How do the two compare? For a list of 5 items, selection sort makes 10 comparisons (4 + 3 + 2 + 1). Bubble sort makes at most 10 comparisons too, but it can stop early if a pass makes no swaps. Neither is fast for long lists — both are roughly N × N work — which is why real systems use faster sorts such as merge sort and quick sort for large data. Sorting is also where stability matters: a stable sort keeps equal items in their original order. Bubble sort, insertion sort and merge sort are stable; selection sort and quick sort are not.

8. Testing: normal, boundary and empty cases

An algorithm is only finished when it has been tested. Good testing uses three kinds of cases. Normal cases are ordinary inputs: a list with several different numbers, a score of 75. Boundary cases are the edges: the smallest and largest allowed values, zero, equal values, and the exact point where a decision changes (49 and 50 for a pass mark of 50). Empty and unusual cases are the ones people forget: an empty list, a list with one item, and input that is missing or in the wrong form.

Trace every test by hand, in a table, and write down what you expected before you check what the algorithm actually does. If the two disagree, the algorithm has a bug — or your expectation is wrong, which is also worth finding out. Testing is not a chore after the work; it is part of designing the algorithm.

Common mistakes to avoid

Mistake 1: Vague steps. Wrong: "Sort the numbers." Correct: "Find the smallest remaining number and swap it into the next position." A step another person cannot follow is not a step.
Mistake 2: Forgetting boundary cases. Wrong: testing only with 80 and 20 when the pass mark is 50. Correct: test 49 and 50 as well — the values on either side of the boundary.
Mistake 3: A decision diamond with unlabelled branches. Wrong: two arrows leaving a diamond with no labels. Correct: label them Yes and No, so the reader knows which path is which.
Mistake 4: Using binary search on an unsorted list. Wrong: binary search on [5, 2, 4, 1, 3] and trusting the answer. Correct: sort the list first, or use linear search.
Mistake 5: A loop that cannot stop. Wrong: "WHILE total is less than 100: ADD 1 TO total" where total never changes inside the loop. Correct: make sure something inside the loop moves the condition towards false.
Mistake 6: Using a value before it is set. Wrong: calculating an average before adding up the total. Correct: create every value before the step that uses it.

Lesson summary

  • An algorithm is a clear, ordered, finite set of steps that solves a problem.
  • Sequence runs steps in order; selection chooses a path; repetition runs steps again.
  • Flowcharts use ovals for start/end, rectangles for processes, parallelograms for input/output and diamonds for decisions.
  • Linear search checks every item; binary search halves a sorted list at each step.
  • Selection sort finds the smallest remaining item each pass; bubble sort swaps neighbours until a pass makes no swaps.
  • Test with normal, boundary and empty cases — and trace by hand in a table.
